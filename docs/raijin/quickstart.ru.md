# Быстрый старт Raijin

Используйте опубликованный пакет и соответствующий ему проверенный Yarn runtime как одну пару. Здесь описаны подключение и повседневные команды; подробное поведение каждой возможности остаётся в README её пакета.

<!-- sync:preflight -->

## 1. Перед началом

- Используйте Node.js `>=24.15.0 <25` и доступный Yarn/Corepack для первоначального вызова `yarn dlx`
- Новый проект создавайте в пустом каталоге; существующий подключайте из корня Yarn-проекта с `package.json`, где указано `"type": "module"`
- Новый проект использует Yarn PnP и ESM. Обновление сохраняет существующие `nodeLinker` и настройки проекта, но не преобразует CommonJS-проект

Релиз `@atls/raijin@0.7.0` содержит старый `yarn.mjs`, а не проверенный `yarn.js`, необходимый новому установщику. Публичные команды `init/update` ниже применимы **после выпуска v2 с соответствующим файлом релиза**. Установщик откажет старому пакету без активации runtime; проверка локально упакованного пакета не доказывает работу публичной установки.

<!-- sync:new-project -->

## 2. Создать проект после выпуска v2

```bash
yarn dlx @atls/raijin init --type project
```

Для библиотеки используйте `--type library`. Установщик выбирает опубликованный пакет и соответствующий файл релиза, проверяет digest runtime, устанавливает пакет и один раз создаёт каркас. Проект записывает проверенный runtime в `.yarn/releases/yarn.js` через `yarnPath`.

Если каталог ещё не является Git-репозиторием, выполните `git init`, затем `yarn install` для включения hooks. Каркас не создаёт правила lint-staged: [настройте их до первого коммита](#staged-checks).

<!-- sync:existing-project -->

## 3. Подключить или обновить существующий проект после выпуска v2

```bash
yarn dlx @atls/raijin update
```

Обновление не запускает каркас и не заменяет настройки TypeScript, ESLint, Prettier или lint-staged. Оно выбирает опубликованный в npm `latest` пакета Raijin и соответствующий ему проверенный runtime и останавливается до записи, если существующий манифест не ESM. В монорепозитории запускайте команду из корня Yarn-проекта с `@atls/raijin`; независимому вложенному Yarn-проекту нужен собственный `yarn.lock`.

Сохраните принадлежащие проекту проверки. Фиксируйте обновлённые манифест, lockfile, `.yarnrc.yml`, проверенный runtime и осмысленные изменения конфигурации одним коммитом.

<!-- sync:bundle-upgrade -->

## 4. Обновить установленную пару

```bash
yarn dlx @atls/raijin update
```

Та же команда выбирает последнюю опубликованную пару пакета Raijin и проверенного runtime. Она приводит `packageManager` к версии Yarn из проверенной ревизии релиза. Отдельное повышение версии зависимости не обновляет проверенный runtime.

## 5. Проверки перед коммитом

Этот шаг обязателен при подключении новых и существующих проектов. Настроенный Git hook вызывает `yarn commit staged`. Raijin не подставляет конфигурацию по умолчанию: без неё проверка подготовленных файлов завершается ошибкой.

Husky 9.1.7 владеет относительным Git `core.hooksPath` в `.config/husky/_`; Raijin устанавливает только помеченные файлы `pre-commit`, `commit-msg` и `prepare-commit-msg`. Если при переключении действующий hook перестал бы запускаться, установка сообщает о конфликте вместо перезаписи. В CI, при упаковке image и с `HUSKY=0` hooks не устанавливаются. Не настраивайте `core.hooksPath` вручную ради Raijin.

Сначала проверьте существующие настройки. Поле `lint-staged` в `package.json`, `.lintstagedrc` в JSON/YAML и `lint-staged.config.*` остаются допустимыми native-форматами. Сохраняйте выбранный формат, команды и исключения проекта; не создавайте конкурирующую конфигурацию.

Если конфигурации ещё нет, ниже пример для одного Raijin PnP/ESM-проекта с TypeScript и тестами `*.test.ts`/`*.spec.ts`, исполняемыми Node. Приспособьте его к проверкам, которые действительно принадлежат вашему проекту:

```json
{
  "*.{yml,yaml,json,graphql,md}": "yarn format",
  "*.{js,mjs,cjs,jsx,ts,tsx}": ["yarn format", "yarn lint"],
  "*.{ts,tsx}": "yarn typecheck",
  "*.{test,spec}.{ts,tsx}": "yarn test unit"
}
```

Каждый самостоятельный Yarn-проект внутри того же Git-репозитория задаёт собственную конфигурацию: lint-staged использует ближайшую и не объединяет её с корневой. Корень не должен незаметно проверять либо пропускать независимого клиента.

Клиент с TypeScript и Jest использует собственный компилятор и `yarn run test`, если его script `test` запускает Jest; зависимость от Raijin ему не требуется. Для проверки всего `tsconfig.json` без добавления staged-путей используйте JS-конфигурацию lint-staged с callback, например `() => "yarn exec tsc --noEmit -p tsconfig.json"`. Конфигурации должны покрывать все обязательные проверки; отсутствие клиентского конфига не должно оставлять его файлы без проверок.

После настройки добавьте конфигурацию и хотя бы один действительно изменённый файл в Git index, затем выполните из корня репозитория:

```bash
yarn commit staged
```

Убедитесь, что проверен каждый затронутый проект, затем сделайте обычный коммит. Пустой staged-набор или отсутствие совпавших файлов не доказывает настройку проверок. Транзакцию и конфликты описывает [владелец commit-команд](../../packages/plugins/commit/README.md).

## 6. Проверить проект

```bash
yarn check
yarn check --verify
yarn check packages/app
```

`yarn check` выполняет Format, Lint, TypeCheck, unit и integration tests активного проекта; форматирование может записывать файлы. `--verify` выполняет ту же политику без записи и сообщает о расхождении форматирования. Каталог ограничивает Format, Lint и тесты, а TypeScript проверяет применимый проект целиком. Проверка одного файла остаётся адресной. Сначала разберитесь с [областями проверки](./verification.md), прежде чем заменять полную проверку адресной.

## 7. Проверить pull request в CI

```yaml
name: Verify
on: pull_request

jobs:
  checks:
    runs-on: ubuntu-latest
    steps:
      - uses: actions/checkout@v7
        with:
          fetch-depth: 0
      - uses: actions/setup-node@v7
        with:
          node-version-file: package.json
      - run: yarn install --immutable
      - run: yarn check --verify --since "$BASE_SHA"
        env:
          BASE_SHA: ${{ github.event.pull_request.base.sha }}
```

Это пример для собственного репозитория потребителя. Git должен содержать базовый коммит PR и историю до merge-base; иначе выбор изменений завершится ошибкой, а не подменится другой областью. Workflow самого Raijin создаются из Terraform-источника в репозитории инфраструктуры: меняйте источник, а не порождённую копию `.github/workflows`. Raijin задаёт политику проверок, Git владеет историей сравнения, Yarn выбирает изменённые и зависящие workspaces, GitHub Actions выполняет workflow.

## 8. Использовать Next.js под Yarn PnP

В проверенном одиночном проекте Next.js 16.3.6 добавьте `"type": "module"` в корневой `package.json` до подключения Raijin. Это задаёт ESM-область пакета для проверенного Yarn runtime; менять исходники стандартного приложения Next не требуется. В монорепозитории ограничьте корневой TypeScript-проект его собственными файлами и сохраните отдельный `tsconfig.json` у Next workspace.

```sh
yarn renderer build
yarn renderer start
yarn renderer dev
```

Raijin передаёт выбранный workspace и поддерживаемые аргументы CLI Next; build и dev используют документированный режим Webpack под PnP. Конфигурация приложения, environment-файлы, результат сборки и сервер остаются у Next. Подробности — у [владельца renderer-команд](../../packages/plugins/renderer/README.md).
